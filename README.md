# 競馬予想カスタムビルダー

「プロ厳選6ファクター」を選択・重み付けしてMy総合指数を算出するインタラクティブ機能一式。

## 構成

- `wordpress-plugin/horse-race-custom-builder/` — WordPressプラグイン本体。既存の Keiba Race Sync
  プラグインが保持する `race_card` データに、新規メタキー `hrc_factors`（6ファクターのスコア）を
  重ね合わせて表示する。keiba-tips.top へデプロイ・動作確認済み。
- `collector/KeibaDataCollector/` — 6ファクター算出用のデータ収集・集計アプリ（C#/.NET
  Framework 4.8、JV-Link/UmaConn連携）。既存の稼働中システム（別リポジトリ
  `keiba-race-result-auto-posting`）をベースに拡張したコピー。**既存の本番リポジトリには一切
  変更を加えていない。**

|---|---|---|---|
| 1 | 枠・馬場バイアス | データ基盤あり（要スコアリング実装） | データ基盤あり（要スコアリング実装） |
| 2 | テン速度・展開 | データ基盤あり（要スコアリング実装） | データ基盤あり（要スコアリング実装） |
| 3 | 上がり3F質・末脚 | データ基盤あり（要スコアリング実装） | データ基盤あり（要スコアリング実装） |
| 4 | 騎手コース回収率 | データ基盤あり（要スコアリング実装） | データ基盤あり（要スコアリング実装） |
| 5 | 血統適性・妙味 | データ取得確認済み（要スコアリング実装・父/母父インデックス未検算） | **提供なし。地方競馬では算出不可** |
| 6 | 調教・加速ラップ | データ取得確認済み（要スコアリング実装） | **提供なし（栗東・美浦は中央競馬専用施設）。地方競馬では算出不可** |

**⚠️ 要お客様確認**: サイトで扱っている門別・川崎・名古屋・園田は全て地方競馬（UmaConn）。
実機のprobeで、SLOP(坂路調教)/WOOD(ウッドチップ調教)/BLOD(血統)がUmaConn側では
一切提供されないことを確認済み（JV-Link/中央競馬側は取得成功）。したがって⑤⑥の2ファクターは、
現状表示している地方競馬のレースには適用できない。中央競馬のレースを扱う場合のみ有効。

「データ基盤」= JV-Link/UmaConnから必要な生データを取得しローカルSQLiteに蓄積する仕組み
（`collector/KeibaDataCollector/Data/HistoricalDataStore.cs`, `Services/BackfillService.cs`）。
**まだ0〜100点のスコアに変換するロジック（統計処理）は実装していない。** WordPress側の
`hrc_factors` へ実際に値を送信する処理も未実装。次フェーズで対応する。

## VPSでの作業手順

### 1. まず probe で確認する（必須）

```
run-probe.bat
```

`SLOP`（坂路調教）・`WOOD`（ウッドチップ調教）・`BLOD`（血統）の3つのdataspec名が、実際に
このJV-Link/UmaConn契約で読めるかを確認する（Normal→ThisWeekAndToday→SetupThisWeekの順に
optionを自動的に試す。JV-Link側はNormalで成功することを実機確認済み）。

**実機確認結果（2026-08-20）**: JV-Link（中央競馬）はSLOP/WOOD/BLODすべて成功
（HC:548,966件, WC:162,857件, SK:8,302件/HN:2,085件）。UmaConn（地方競馬）は3つとも
提供なし（rc=-1または-111）。地方競馬では⑤⑥ファクターは算出できないことが確定した。

**dataspec名の訂正**: 当初コードで使っていた`BLDN`は誤りで、正しくは`BLOD`
（JRA-VAN公式のJV-Data仕様書 `JV-Data470.xlsx`「データ種別一覧」シートで確認）。
同シートには以下も明記されている。
- `SLOP`（坂路調教）: 2003年以降のデータを提供
- `WOOD`（ウッドチップ調教）: **2021年7月27日以降のみ**（それ以前は無い。ただしお客様の
  「過去3年」基準には収まる）
- `BLOD`（血統）: 1986年以降のデータを提供
- 「JVOpenで指定可能なoptionとdataspecの関係」表では、`BLOD`/`SLOP`/`WOOD`はいずれも
  option=1（通常データ）・option=3,4（セットアップ）の**両方で有効**と明記されている

**判明した事実（2026-08-20、実機ログで確認）**: `option=1`（通常データ）は「有効な組み合わせ」
ではあるが、実際には**直近およそ1年分しか返さない**（SLOP/WOODとも日付範囲が
`2025-08-19〜2026-08-20`の丁度1年だった）。全履歴を取るには`option=3`（Setup）が必要。
JV-Link側ではSetupをまだ試していなかった（Normalで先に成功していたため）。

**過去3年で十分との方針決定を受けて**: お客様から「過去3年分で分析すればよい」と
確認が取れたため、`BackfillFromTime`を1986年固定から**実行日の3年前**に変更した
（`BackfillService.cs`）。SLOP実測値（1年で約55万件）から換算すると、3年分で
約165万件程度の想定（23年分・約1260万件よりはるかに現実的）。ただしfromtimeが
Setupモードの絞り込みに実際に効くかは未検証（開発者コミュニティには効くという報告があるのみ）。
効かず全件返ってきた場合は取り込み時にRaceDate等でフィルタする対応に切り替える。

### 2. バックフィル実行（時間がかかる。要スケジュール確保）

```
run-backfill.bat
```

過去3年分（`BackfillFromTime`、JVOpenのSetupオプション）を取得する。中央・地方あわせて、
件数は数十万〜数百万レコード規模になりうるため、**数時間かかる可能性がある。**
`data\historical.sqlite3` に蓄積される。中央競馬のみ／地方競馬のみに絞りたい場合は
`run-backfill.bat jv` / `run-backfill.bat uma`。完了後のログで「日付範囲」が
本当に3年分（またはそれに近い範囲）に収まっているか確認すること。

### 3. 血統の父・母父インデックスを検算する（要対応・未実装）

`JvFactorRecordParser.ParseOffspringPedigree` は、産駒マスタ(SK)のHansyokuNum[14]配列を
「0:父 1:母 2:父父 3:父母 4:母父 5:母母...」という並びで読んでいるが、これは公式一次仕様書
そのものでは確認できず、複数の非公式情報源の一致に基づく前提。血統適性ロジックを書く前に、
既知の有名馬のKettoNumでこの並びが実際の血統と一致するか確認すること。

### 4. スコアリングロジックの実装（次フェーズ・未着手）

`historical.sqlite3` を集計し、6ファクターを0〜100点に正規化した上で、WordPress側の
`hrc_factors` メタへ送信する処理。クライアント様からいただいた基準（過去3年の枠番別連対率等）
に基づいて実装する。
