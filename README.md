# 競馬予想カスタムビルダー

「プロ厳選6ファクター」を選択・重み付けしてMy総合指数を算出するインタラクティブ機能一式。

## 構成

- `wordpress-plugin/horse-race-custom-builder/` — WordPressプラグイン本体。既存の Keiba Race Sync
  プラグインが保持する `race_card` データに、新規メタキー `hrc_factors`（6ファクターのスコア）を
  重ね合わせて表示する。keiba-tips.top へデプロイ・動作確認済み。
- `collector/KeibaDataCollector/` — 6ファクター算出用のデータ収集・集計アプリ（C#/.NET
  Framework 4.8、JV-Link/UmaConn連携）。既存の稼働中システム（別リポジトリ
  `keiba-race-result-auto-posting`）をベースに拡張したコピー。**既存の本番リポジトリには一切
  変更を加えていない。**

## 6ファクターの現状（2026-08-24時点）

`FactorScoringService.cs`でスコアリングロジックを実装し、`score`コマンド
（`FactorPublishService.cs`）で当日出走馬の6ファクターをWordPressの`hrc_factors`へ
送信できるところまで実装済み。母集団平均50点・標準偏差10点あたりの偏差値スタイルで
0〜100点に正規化している（サンプル数が`MinGroupSample`未満の集団は信頼できないため、
無理に数値を出さずnullを返す）。

| # | ファクター | 実装状況 |
|---|---|---|
| 1 | 枠・馬場バイアス | 実装済み。コース別枠番連対率を偏差値化 |
| 2 | テン速度・展開 | 実装済み（新規実装。後述）。**要再backfill** |
| 3 | 上がり3F質・末脚 | 実装済み。直近5走の上がり3F平均を、馬場種別内で偏差値化 |
| 4 | 騎手コース回収率 | 実装済み（原因調査・修正済み。後述）。**要再backfill**。コース別騎手複勝回収率（HR払戻を反映）を偏差値化 |
| 5 | 血統適性・妙味 | 実装済み（dataspec名の誤り(BLOD→BLDN)を修正済み。後述）。**要再backfill** |
| 6 | 調教・加速ラップ | 実装済み。直近の調教のラスト1Fタイム＋加速ラップ判定 |

**中央競馬(JV-Link)と地方競馬(UmaConn)の違い**: サイトで扱っている門別・川崎・名古屋・園田・
福山・北見等は全て地方競馬。実機のprobeで、SLOP(坂路調教)/WOOD(ウッドチップ調教)/BLOD(血統)が
UmaConn側では一切提供されないことを確認済み（JV-Link/中央競馬側は取得成功）。
実機の`score`結果（2026-08-24、UmaConnのみ596頭）でも、⑥調教・加速ラップは242/596件
（約41%）しか値が付かなかった。地方競馬の馬が過去に中央競馬で調教を受けた記録がある場合
のみ値が付くと考えられ、地方競馬の馬の大半は坂路・ウッドチップ調教のセンサーが無い施設で
調教されているため、構造上ここが上限に近いと考えられる（UmaConn側に地方競馬独自の調教
データ種別が無いか、別途確認の余地あり）。⑤血統は前述のBLDN修正でUmaConn側の対応状況は
未確認（次回backfill時にprobeログで確認すること）。

**解決済みの問題（履歴）**:
- **④騎手コース回収率が全馬50点固定になっていた不具合**: 実機診断で2段階の原因が判明し、
  両方とも修正済み。
  1. `race_entries`の複勝払戻UPDATE（`UpdateFukushoPayout`）が`(race_date, track_code,
     distance, umaban)`だけで対象行を絞り込んでいた。地方競馬は同日・同競馬場で距離が同じ
     レースが複数あるのが普通のため、この条件では別レースの馬にまで払戻額が誤爆しうる。
     → `race_entries`に`race_number`列を追加し、突き合わせ条件に加えて解消。
  2. race_number追加後も`複勝払戻を反映した行=0`のままだった。実機ログで
     `RACE進捗: 5000件処理（SE:0 RA:0 HR:264)`という診断が取れ、**JV-Data(RACE dataspec,
     Setup)は「RA→SE→HRの順で届く」という前提が成り立たない**（同日内でHRがRA/SEより先に
     届くケースが実際にある）ことが判明した。当時のコードはHRが来た時点でその場で
     `race_entries`をUPDATEしようとしていたため、対象行がまだ存在せず常に0件更新になっていた。
     → HRの複勝payoutは一旦メモリ上のリストに溜めるだけにし、RACEストリーム全体を読み終えて
     `race_entries`が確実に埋まった後で、まとめてUPDATEする2パス方式に変更して解消。
     `UpdateFukushoPayout`はdistance引数が不要になった（race_numberだけで一意に絞り込めるため）
     ので削除し、実際に反映できた行数を返り値で返すようにした（呼び出し側で
     `対象行が見つからなかった数`として検証できる）。
- **⑤血統の`pedigree_links`が0件だった不具合（dataspec名の誤り）**: `BackfillPedigree()`が
  `BLOD`をSetup Openすると常に`rc=-1`（該当データなし）になっていた。JRA-VAN公式JV-Data
  仕様書Ver.4.9.0.1（データ種別一覧シート・変更履歴シート）で確認したところ、
  「蓄積系ソフト用 血統情報」のdataspecは2023年8月8日の18.繁殖馬マスタ項目拡張
  （繁殖登録番号等が8バイト→10バイト）を境に`BLOD`（それ以前のデータのみ）と`BLDN`
  （2023-08-08以降のデータのみ）に分かれており、`BackfillFromTime`（実行日の3年前）は
  常に2023-08-08より後になるため、`BLOD`には該当データが無かった（該当データなし＝バグでは
  なく、要求した期間がそもそもそのdataspecの提供範囲外だった）。加えて、既存の
  `JV_HN_HANSYOKU`/`JV_SK_SANKU`構造体は既に10バイト形式でパースする実装になっており
  （レコード長251/208バイトが現行仕様と一致）、これは新フォーマット（`BLDN`）向けだった。
  → dataspec名を`BLOD`から`BLDN`に変更して解消（`BackfillService.BackfillPedigree()`、
  `DataSpecProbeService.SetupSpecsToProbe`）。
- **②テン速度・展開の新規実装**: クライアント基準「近3走の前半3Fタイム・脚質実績からの
  先行有利度」に対応。個体（1頭）ごとの前半3Fタイムはrace_entriesに保持していないため、
  代わりにRAレコードのコーナー通過順位（Jyuni）から「最も早いコーナーでの通過順位を
  0〜1に正規化した値」（`early_position_ratio`列、0=先頭通過・1=最後尾通過）を脚質実績の
  代理指標として新規に収集・保存するようにした（`JvFactorRecordParser.ParseEarliestCornerOrder`、
  `BackfillService`）。通過順位テキストの記法（集団は`()`、大差`=`、小差`-`、先頭馬`*`）は
  JV-Data仕様書Ver.4.9.0.1で確認済みだが、実装では前後関係（左から右の順序）のみを使い、
  集団内の微妙な差までは区別しない単純化をしている。
  スコアリング（`FactorScoringService.ComputePaceScore`）は、①対象馬の直近3走の
  early_position_ratio平均（先行傾向）と、②当該コース(track×distance×surface)で複勝圏内の馬が
  実際に前目を通過している傾向があるか（先行有利なコースかどうか）を組み合わせ、
  先行有利なコースでは前目に付ける馬を高得点に、そうでなければ低く評価する。
- RACE dataspecのSetup取得で`rc=-501`（スタートキット関連。2022年3月に提供終了した
  スタートキットを探しに行ってしまう不具合の可能性）が発生することがある。再実行時に
  セットアップダイアログが出たら「スタートキットを持っていない」を選ぶこと

## VPSでの作業手順

### 1. まず probe で確認する（必須）

```
run-probe.bat
```

`SLOP`（坂路調教）・`WOOD`（ウッドチップ調教）・`BLDN`（血統）の3つのdataspec名が、実際に
このJV-Link/UmaConn契約で読めるかを確認する（Normal→ThisWeekAndToday→SetupThisWeekの順に
optionを自動的に試す。JV-Link側はNormalで成功することを実機確認済み）。

**実機確認結果（2026-08-20）**: JV-Link（中央競馬）はSLOP/WOOD/BLOD(当時)すべて成功
（HC:548,966件, WC:162,857件, SK:8,302件/HN:2,085件）。UmaConn（地方競馬）は3つとも
提供なし（rc=-1または-111）。

**dataspec名について（2026-08-20時点の結論は誤りだったため訂正・2026-08-24）**:
2026-08-20時点では、JRA-VAN公式のJV-Data仕様書の古いバージョン(`JV-Data470.xlsx`)のみを
参照し、「当初コードで使っていた`BLDN`は誤りで、正しくは`BLOD`」と判断してコードを
修正していた。しかしその後、`BackfillPedigree()`の`BLOD` Setup Openが常に
`rc=-1`（該当データなし）になる問題を調査する過程で、最新の公式仕様書
（JV-Data仕様書Ver.4.9.0.1、2024-08-07付、`https://jra-van.jp/dlb/sdv/sdk/JV-Data4901.xlsx`
からダウンロードして確認）を参照したところ、`BLOD`と`BLDN`は**どちらも実在する正しい
dataspec名**で、2023年8月8日の18.繁殖馬マスタ項目拡張（繁殖登録番号等が8バイト→10バイト）
を境に提供範囲が分かれていることが判明した（`BLOD`=それ以前のデータのみ、`BLDN`=
2023-08-08以降のデータのみ）。このプロジェクトの`BackfillFromTime`（実行日の3年前）は
常に2023-08-08より後になるため、正しいdataspecは`BLDN`だった。コードは`BLDN`に戻して
解消済み（上の「解決済みの問題」参照）。
- `SLOP`（坂路調教）: 2003年以降のデータを提供
- `WOOD`（ウッドチップ調教）: **2021年7月27日以降のみ**（それ以前は無い。ただしお客様の
  「過去3年」基準には収まる）
- `BLOD`（血統・旧形式）: 1986年以降〜2023-08-08より前のデータを提供
- `BLDN`（血統・新形式）: 2023-08-08以降のデータを提供
- 「JVOpenで指定可能なoptionとdataspecの関係」表では、`BLOD`/`BLDN`/`SLOP`/`WOOD`は
  いずれもoption=1（通常データ）・option=3,4（セットアップ）の**両方で有効**と明記されている

**判明した事実（2026-08-20、実機ログで確認）**: `option=1`（通常データ）は「有効な組み合わせ」
ではあるが、実際には**直近およそ1年分しか返さない**（SLOP/WOODとも日付範囲が
`2025-08-19〜2026-08-20`の丁度1年だった）。全履歴を取るには`option=3`（Setup）が必要。
JV-Link側ではSetupをまだ試していなかった（Normalで先に成功していたため）。

**過去3年で十分との方針決定を受けて**: お客様から「過去3年分で分析すればよい」と
確認が取れたため、`BackfillFromTime`を1986年固定から**実行日の3年前**に変更した
（`BackfillService.cs`）。SLOP実測値（1年で約55万件）から換算すると、3年分で
約165万件程度の想定（23年分・約1260万件よりはるかに現実的）。ただしfromtimeが
Setupモードの絞り込みに実際に効くかは未検証（開発者コミュニティには効くという報告があるのみ）。
効かず全件返ってきた場合は取り込み時にRaceDate等でフィルタする対応に切り替える。

### 2. バックフィル実行（時間がかかる。要スケジュール確保）

```
run-backfill.bat
```

過去3年分（`BackfillFromTime`、JVOpenのSetupオプション）を取得する。中央・地方あわせて、
件数は数十万〜数百万レコード規模になりうるため、**数時間かかる可能性がある。**
`data\historical.sqlite3` に蓄積される。中央競馬のみ／地方競馬のみに絞りたい場合は
`run-backfill.bat jv` / `run-backfill.bat uma`。完了後のログで「日付範囲」が
本当に3年分（またはそれに近い範囲）に収まっているか確認すること。

### 3. 血統の父・母父インデックス（検証済み）

`JvFactorRecordParser.ParseOffspringPedigree` は、産駒マスタ(SK)のHansyokuNum[14]配列を
「0:父 1:母 2:父父 3:父母 4:母父 5:母母...」という並びで読んでいる。JRA-VAN公式の
JV-Data仕様書Ver.4.9.0.1（フォーマットシート、19.産駒マスタ・項番13）に
「父･母･父父･父母･母父･母母･父父父･父父母･父母父･父母母･母父父･母父母･母母父･母母母の順に設定」
と明記されており、このコードの前提と一致することを確認済み。

### 4. スコアリングと配信（実装済み）

`historical.sqlite3` を集計し、6ファクターを0〜100点に正規化した上で、`score`コマンド
（`FactorPublishService.cs`）でWordPress側の`hrc_factors`メタへ送信する。
クライアント様からいただいた基準（過去3年の枠番別連対率・回収率等）に基づいて実装している。
`run-score.bat`を実行する。
