# KeibaDataCollector

JV-Link（中央競馬）とUmaConn（地方競馬DATA／競馬最強の法則WEB）から出走表・結果データを取得し、
WordPressへ自動反映するWindows常駐アプリの土台。

## 前提・設計方針

- JV-LinkとUmaConnは**同一仕様（JV-Link Interface Specification）のCOMコンポーネント**なので、
  `Interop/JvSpecComDataSource.cs` 1つで両方を扱う（ProgIDだけが違う）。
- JV-Link/UmaConnは**32bit専用**。ビルド設定は `PlatformTarget=x86` 固定（csproj設定済み）。
- COMは後期バインド（ProgID + リフレクション）で呼んでいる。理由: 環境依存のインタロップ型名を
  この開発環境では検証できないため。副作用として、COMイベント（JVWatchEvent等）は使えないので、
  結果監視は**ポーリング方式**にしている（`RaceResultService`）。

## 実機で必ず確認・修正が必要な項目（★重要）

1. ~~**UmaConnの正確なProgID**~~ → 実機のレジストリで確認済み: `NVDTLabLib.NVLink`（`App.config`反映済み）。
   `setup`コマンドでUmaConn側のダイアログも開くことを確認済み。
2. ~~**メソッド名のプレフィックス**~~ → 実機で `New-Object -ComObject` + `Get-Member`により、
   JV-LinkとUmaConnは同じメソッド一覧を `JV*`/`NV*` のプレフィックス違いで持つことを確認済み
   （`JvSpecComDataSource`にmethodPrefix引数として反映済み）。
3. ~~**JVOpen / JVRead 等の引数の正確な型・並び順**~~ → JRA-VAN公式のJV-Linkインターフェース仕様書
   （`JV-Linkインターフェース仕様書_4.9.0.1(Win).pdf`）で確認済み。既存の実装のシグネチャと一致。
4. ~~**レコードのバイトレベルパース**~~ → JRA-VAN公式SDKの `JVData_Struct.cs` を入手し
   `Interop/JvDataSdk/JVData_Struct.cs` に配置、`JvRecordParser` から `SetDataB()` を呼ぶ形で実装済み。
   `RaceCardService`/`RaceResultService` から `WordPressClient` への配線も完了。
   **残課題**: `ChakusaCD`（着差コード、数値）をハナ/クビ/アタマ等の表示文字列に変換するコード表が
   未確認（SDK同梱ドキュメントには見当たらず）。現状は生コードをそのまま`ChakusaText`に出している。
5. ~~**リアルタイム系データ種別コード**~~ → JV-Linkインターフェース仕様書「JVRTOpen」の対応表で確認済み。
   払戻確定＝`0B12`で、既存の仮実装の値がそのまま正しかった。
6. **JVSetServiceKey の要否** → 実機で`JVSetUIProperties`（`setup`）による利用キー登録が成功したため、
   通常はこちらの方式のみで運用可能と思われる（`JVSetServiceKey`を明示的に呼ぶ実装は現状なし）。

## 実機での既知の問題と対応

- **JRA-VAN利用キーは1台のPCにしか紐付けられない**（データラボサービスの仕様）。
  複数PCで同じ利用キーを使うと「認証エラー：この利用キーは既に使用されています」となる。
  発生した場合は JRA-VAN Data Lab.のマイページで利用キーの再発行が必要（該当PCのJV-Link
  アンインストール→再インストールも必要になる場合がある）。
- Windowsの「システムロケール」（Unicode対応をしていないプログラムの言語）が日本語でないと、
  JV-Linkのネイティブダイアログが文字化けする。`intl.cpl` → 管理タブ → システムロケールの変更 →
  日本語（日本）に変更し、PC再起動が必要。

## WordPress側で別途必要な準備

- カスタム投稿タイプ `race` を `show_in_rest: true` で登録
- `race_key` / `race_card` / `race_result` / `payouts` / `corner_passage` を
  `register_post_meta` でREST読み書き許可
- 対象ユーザーで [アプリケーションパスワード](https://ja.wordpress.org/support/article/introduction-to-application-passwords/) を発行

これは別途 `functions.php` またはコンパニオンプラグインとして用意する想定（未着手）。

## 実行方法

```
KeibaDataCollector.exe setup    # 初回のみ。利用キー等をGUIダイアログで登録
KeibaDataCollector.exe morning  # 朝一: 当日の出走表取得→WordPress反映
KeibaDataCollector.exe watch    # レース確定監視→結果・払戻を随時反映
KeibaDataCollector.exe probe    # 調査用: どのデータ種別で何が取れるか確認（WordPressへ書き込まない）
```

対話的に動かす場合は同名の `run-*.bat` から起動できます。

## 自動運用（タスクスケジューラ）

### 前提：`setup` を実行したユーザーで動かすこと

JV-Link / UmaConn の利用キーは **`setup` を実行したWindowsユーザーのレジストリ**に
保存されます。別ユーザーでタスクを動かすと認証エラー（-301/-303）になります。
登録スクリプトは実行中のユーザー自身を登録するため、**VPSに`setup`したユーザーで
ログインしてから**実行してください。

### 登録

```powershell
cd (作業ディレクトリ)\src\KeibaDataCollector
powershell -ExecutionPolicy Bypass -File .\register-scheduled-tasks.ps1
```

既定で以下の2タスクを作成します（時刻は `-MorningTime` / `-WatchTime` で変更可）。

| タスク名 | 既定時刻 | 内容 |
| --- | --- | --- |
| `KeibaDataCollector-Morning` | 毎日 07:00 | 当日の出走表を取得・反映 |
| `KeibaDataCollector-Predict` | 毎日 09:00 から15分ごと×12時間 | オッズの人気順から予想印を生成・反映 |
| `KeibaDataCollector-Watch` | 毎日 09:30 | 確定監視。全レース確定で自動終了 |

`watch` は当日の全レースが確定すると自分で終了するため、停止トリガーは不要です。
多重起動は禁止設定（同じCOMを二重に開かないため）にしています。

### 日中に登録し直すときの注意

**タスク定義を置き換えると、実行中のインスタンスはその場で終了します。**
`watch` はトリガーが1日1回（09:30）しかないため、日中に登録し直すと
**その日はもう再開せず、以降のレース結果が反映されないまま終わります。**

実際に発生しました（2026-08-11）。15:10にこのスクリプトを再実行した結果、
結果の反映が57レース中18レースで止まり、お客様から
「結果が表示されているレースと、されていないレースがある」とご指摘をいただきました。

登録スクリプトは**実行中だったタスクを登録後に自動で再開する**ようにしてあります。
出力に `実行中だったため再開します: KeibaDataCollector-Watch` が出れば再開済みです。

なお `watch` は起動時にレース一覧を取り直し、確定済みのレースをまとめて反映します。
速報レース情報(0B12)の提供期間は1週間（JV-Data仕様書）なので、
**同日中に再開すれば取りこぼしたレースは追いつきます。**

### スケジューラ用スクリプトを別に用意している理由

`run-*.bat` は末尾に `pause` があり、**タスクスケジューラから実行すると
キー入力待ちでタスクが終了しません**（翌日のトリガーもスキップされる）。
そのため `scheduled-morning.bat` / `scheduled-watch.bat` を別に用意し、
`pause` を外して `logs\` へ日付ごとにログ出力するようにしています。

### 更新の反映

**修正を本番へ反映するときは、これだけ実行してください。**

```powershell
cd (作業ディレクトリ)\src\KeibaDataCollector
powershell -ExecutionPolicy Bypass -File .\deploy.ps1
```

「停止 → 取得 → ビルド → タスク登録 → 再開」を必ずこの順で行います。

**手順を都度組み立てないでください。**実際に次の失敗を繰り返しました。

- **稼働中に `dotnet build` を実行するとビルドが失敗します。**
  exeがロックされ `別のプロセスが使用中のため…にコピーできませんでした` になります。
  さらに失敗に気づかず再開すると、**修正前のexeがそのまま動き続けます**。
- `Stop-ScheduledTask` は起動用バッチを止めるだけで、
  そこから起動された `KeibaDataCollector.exe` が残ることがあります。
- **タスク定義を置き換えると実行中のインスタンスが終了します。**
  詳細は上記「日中に登録し直すときの注意」を参照。

ビルドに失敗した場合、スクリプトはタスクを再開せずに中断します。
修正前のexeで動き続けるほうが、止まっているより気づきにくく害が大きいためです。

スケジュール（時刻・間隔）を変えていないときは `-SkipRegister` で登録を省略できます。

### 確認・トラブルシュート

```powershell
Get-ScheduledTask -TaskName 'KeibaDataCollector-*' | Format-Table TaskName,State
Start-ScheduledTask -TaskName 'KeibaDataCollector-Morning'      # 手動で試運転
Get-ScheduledTaskInfo -TaskName 'KeibaDataCollector-Morning'    # 前回結果
Get-Content .\logs\morning-*.log -Tail 50 -Encoding UTF8         # 実行ログ
```

**ログは必ず `-Encoding UTF8` を付けて読んでください。**
`scheduled-*.bat` は `chcp 65001` の下でアプリのUTF-8出力をファイルへ流していますが、
Windows PowerShell 5.1 の `Get-Content` は既定でANSI(CP932)として読むため、
付けないと日本語が文字化けします（ファイル自体は壊れていません）。

`LastTaskResult` の主な値:

| 値 | 16進 | 意味 |
| --- | --- | --- |
| `0` | `0x0` | 正常終了 |
| `267009` | `0x41301` | **まだ実行中**（エラーではない。少し待って再確認） |
| `267011` | `0x41303` | 一度も実行されていない |
| `1` | `0x1` | スクリプトが `exit /b 1` で失敗（ログの `[ERROR]` 行を確認） |

### 無人実行時のダイアログ対策

JV-Link / UmaConn はモーダルダイアログを出すことがあり、**出たままだと
ユーザー操作待ちでプロセスが停止**します。以下を実施済み／実施してください。

- 払戻ダイアログ：`m_payflag = 1` をコード側で設定済み（`JvSpecComDataSource.Initialize`）
- 「JRA-VANからのお知らせを表示する」：`setup` のダイアログで**チェックを外す**
- UmaConn終了時のメモリリークダイアログ：発生する場合あり。**未解決**

上記の懸念があるため、登録スクリプトの既定は「**ログオン時のみ実行**」です。
VPSにログインしたセッションを維持（RDPは「切断」でログオフしない）して運用してください。
ダイアログ要因を解消できたら `-RunOnlyWhenLoggedOn:$false` で
「ログオンしていなくても実行」に切り替えられます（パスワード保存が必要）。

## 複数システムの同時実行（JV-Link共通ロック）と起動時刻

### 何が起きていたか（2026-10-25）

このVPSでは3つのシステム、およそ17本のタスクが、同じJV-Link/UmaConnと同じ本番サイトを使っている
（タスク名の系統は `KeibaDataCollector-*`／`HRC *`、`KeibaAiDataSystem-*`〔`C:\keiba-ai-data-system`〕、
`HorseRacingPrediction`。どの系統がどのシステムかは、タスクの「操作」の実行パスで確認すること）。
タスクスケジューラのトリガーを数えると、**毎時0分に5〜7本、9:00には7本が一斉に起動**する
（15・20・30分おきの繰り返しが同じ分に揃っているため。2026-10-05時点の一覧から）。

その結果、`HRC Score` は21:00に起動した回で、JRAの36レースを約20分で終えたあと
地方側の`NVInit`が「シェル通知アイコンが削除できません」で失敗し、約16分の空白を挟み、
**開始からちょうど1時間（上限 `PT1H`）で強制終了**されていた
（`LastTaskResult 267014`＝0x41306）。同日の全8回に`score batch end`行が無く、
1回も自力で終わっていなかった。`HRC Backfill`も同じく強制終了されている。

**強制終了はJV-Linkのダウンロード中に起きると、キャッシュが壊れて`-402`になる**
（上の「解決済みの問題」参照）。キャッシュは全システムで共有するため、他システムも巻き込む。
タスクの実行時間上限は「通常の所要時間に十分な余裕を足したもの」にし、安全弁としてだけ使うこと。

### 対策1: 取得セッションの共通ロック（コード）

`Interop/JvSessionLock.cs`。`JvSpecComDataSource`の `Initialize`、`Open`、`OpenRealtime` で
ロックを取り、`Close`で解放する。ロックファイルは既定で
`C:\ProgramData\KeibaJvLock\jvlink.lock`（環境変数 `JV_LOCK_PATH` で変更可）。

- 取れなければ**待つ**（順番待ち）。時刻に頼らないので、所要時間が日によって変わっても重ならない。
- 待ちには上限がある（Init 5分 / Open 30分 / 速報系 90秒）。**超えたらロックなしで続行する**
  （fail-open）。他システムが長く持っていても、結果反映や予想が止まりきらない。
- プロセスが落ちればOSがロックを解放する。保持者はロックファイルに書かれていて、
  `type C:\ProgramData\KeibaJvLock\jvlink.lock` で保持中でも読める。
- ログに `[jvlock]` で待ちが出る。待ちが頻発する、または上限超過が出る場合は、
  起動時刻か実行回数を見直す合図。
- スコア計算（重い処理）はCloseの後なので、ロックを持ったまま計算することはない。

**ロックは全システムが使って初めて効く。** このリポジトリのexeだけが取っても、他システムは
無関係に動く。同じロックを他システムにも入れる方法は2つ:

1. コードを直せるシステムは、`JvSessionLock.cs`を取り込み、COMラッパーのInit/Open/RTOpenで
   取得、Closeで解放する（このリポジトリの`JvSpecComDataSource`の差分と同じ）。
2. 直せないものは、`run-with-jvlock.ps1`でタスクごと包む。**包むのはJV-Link/UmaConnを使う
   バッチだけ**にする（死活監視・ダッシュボード・バックアップ等を包むと不要な順番待ちが出る。
   常駐のwatchや、このリポジトリのexeを動かすタスクも包まない）。
   どのタスクがJV-Linkを使うかは、各システムの`scheduled-*.bat`が呼ぶモードと、
   ソース内の `JVInit|NVInit|JvSpecComDataSource` の有無で確認する。

### 対策2: 起動時刻と実行回数（`rebalance-schedule.ps1`）

既定は確認だけ。`-Apply`で変更、`-IncludeOtherSystems`で他システムの起動分もずらす。
実行中のタスクは変更しない。

| タスク | 変更前 | 変更後 | 理由 |
|---|---|---|---|
| HRC Score | 6:00起点の3時間おき（8回/日）、上限1時間 | 7:26・10:26・13:26・16:26の4回、上限2時間30分 | 0〜6時は出走表が無く全て無駄。:26は他の起動と重ならない分 |
| HRC Backfill | 月曜4:30、上限は短く強制終了 | 月曜3:30、上限3時間30分 | 7:00に他の定期処理が始まる前に終える |
| KeibaAiDataSystem-Content | 7:40起点・20分おき | 7:43起点（:03 :23 :43） | :00の一斉起動を外す |
| KeibaAiDataSystem-HealthCheck | 8:30起点・15分おき | 8:37起点（:07 :22 :37 :52） | 同上 |
| KeibaAiDataSystem-Dashboard | 7:00起点・30分おき | 7:11起点（:11 :41） | 同上 |
| KeibaAiDataSystem-Score | 7:30起点・20分おき | 7:34起点（:14 :34 :54） | 同上 |
| HorseRacingPrediction | 9:00 | 9:06 | 9:00の7本同時起動を外す |

動かさないもの（時刻に意味がある可能性がある）: KeibaDataCollector-Predict（9:00起点15分おき）、
KeibaAiDataSystem-TrendLive（9:00起点30分おき）・TrendMorning（7:45）・TrendFinal（21:30）・
Verify（22:00）・Backup（1:30）・BackfillIncremental（2:00）、KeibaDataCollector-Morning（7:00）・
Watch（常駐）。この結果、毎時`:00`に実際に起動するのはPredictとTrendLiveの2本だけになる
（Watchの10分おきのトリガーは、常駐中は多重起動禁止で無視される）。

**この時刻は「同時起動を避ける目安」。** 所要時間は日によって大きく変わるので、重なりを
確実に防ぐのは対策1のロックである。所要時間のログ（`RACE読み込み 所要 ○分`、
`採点・反映 所要 ○分`）を数日見て、まだ待ちが多いタスクの回数を減らしていく。

### 運用の手順

1. 反映後、`powershell -ExecutionPolicy Bypass -File .\rebalance-schedule.ps1`（確認のみ）で差分を見る。
2. 問題なければ `-Apply`。他システムの時刻に意図がないことを確認してから `-IncludeOtherSystems`。
3. `deploy.ps1`でexeを更新する（ビルドに失敗すると、タスクを再開せず中断する）。
4. 翌日、`score-*.log`に `score batch end (exit=0)` が出ているか、`[jvlock]`の待ちが
   どの程度出ているかを確認する。

## 予想印（◎○▲△）の生成

予想はJV-Link/UmaConnからは提供されません。お客様が別ツールで
「朝一時点のオッズから人気順に印を付ける」運用をされていたものを、
こちらのデータで直接生成する方式に置き換えたものです（`predict`モード）。

### ルールの根拠

お客様が公開されていた予想26レース分と、当方のオッズデータを突き合わせて確認しました。

| 確認項目 | 実測 |
| --- | --- |
| 印の数 | 全レースで必ず4頭（◎○▲△） |
| 印の付いた馬が確定人気5位以内 | 87.1% |
| 確定人気上位4頭との重なり | 全レースで2頭以上、9レースで4頭全一致 |

ずれは朝から発走までのオッズ変動で説明がつきます。特別なロジックはありません。

### なぜ1日に何度も実行するのか（仕様上の制約）

**オッズは「発売開始前」には存在しません。** JV-Data仕様書「（２）速報系データ」より:

| データ種別 | 提供単位 | 提供タイミング |
| --- | --- | --- |
| 0B31 速報オッズ（単複枠） | **レース毎** | **対象レースの勝ち馬投票券発売以降に提供** |
| 0B30 速報オッズ（全賭式） | レース毎 | 同上 |

重要な帰結が2つあります。

- **データ種別を変えても解決しません。** 0B30に切り替えても「発売以降」の制約は同じです。
- **全レースを一度に取ることはできません。** 0B31の提供単位は「レース毎」のみで、
  0B12や0B11のような「開催日単位（同一開催日の全開催場の全レース）」は選べません。

発売開始の時刻は競馬場ごとに違います。2026-08-11の実測:

| 時刻 | 予想を生成できたレース |
| --- | --- |
| 09:31 | 57件中 **2件**（盛岡10R・浦和11R。いずれも前日発売のある主要レース） |
| 10:05 | 57件中 **24件**（盛岡12/12・笠松11/11・浦和1/12） |
| 12:32 | 57件中 **24件**（浦和・門別・金沢は発売前で0件のまま） |

そのため予想生成は09:00から**15分ごとに12時間（21:00まで）**繰り返し、
発売が始まったレースから順に埋めます。**門別のナイターは最終レースが20時台**のため、
ここを短くすると発売の遅い競馬場の後半レースに予想が付かないまま終わります。
**既に予想が入っているレースは上書きしません**（`UpsertPredictionsAsync` が false を返す）。
上書きすると、オッズが早く揃ったレースほど発走直前の値で塗り替えられ、
「朝一時点のオッズによる人気順」という本来の意味から離れていくためです。

**確定済みのレースも飛ばします**（`ShouldSkipPredictionAsync`）。速さのためだけでなく、
終わったレースのオッズは確定オッズなので、それで印を付けると
「結果を見てから当てた予想」を載せることになるためです。

### 反映までの遅れ

遅れは「繰り返し間隔＋1回の実行時間」になります。実測（2026-08-12）で
1回の実行に23分かかり、30分間隔と合わせて最悪50分ほど遅れ、
お客様から「オッズは公開されているのに予想が出ない」とご指摘をいただきました。

間隔を15分に短縮し、確定済みレースを飛ばすようにしています。
**ログに所要時間を出しているので、間隔を超えていないか必ず確認してください。**
超えると次の回が多重起動禁止で弾かれ、遅れがそのまま伸びます。

```
予想の反映完了: 新規◯件 / 反映済み◯件 / 発売前◯件 / オッズ取得エラー◯件 / 反映失敗◯件 （所要 ◯分）
```

「1件も生成できなかった」を常に異常扱いにすると、毎朝1本目が必ず失敗し、
警報として機能しなくなります。**11時を過ぎても1件も無い場合のみ**異常終了します。

### 別ツールのページを解析しない理由

当初「生成済みページのHTMLを解析する」案がありましたが採用していません。
生成側の書式が少し変わるだけで予想が丸ごと消え、しかも朝9時に静かに壊れるため
気付くのが遅れます。元データ（オッズ）が同じなら自前で生成するほうが安全で、
ばんえい・中央競馬も自動的に対象にできます。

1件も生成できなかった場合は例外にしています。黙って正常終了すると
「予想が出ていないこと」に誰も気付けないためです。

### LINE限定レース

重賞などで予想をLINEで先行公開する場合、管理画面のレース編集画面にある
**「このレースの予想はLINE限定にする」**にチェックを入れると、サイト上では印を伏せて
案内文を表示します。

どのレースをLINE限定にするかはその日ごとの編集判断のため、グレードコードによる
自動判定ではなくレース単位の指定にしています（全重賞を自動で隠すと、
LINE限定にしていない重賞まで予想が消えるため）。

このフラグは収集アプリ側から送らないので、翌朝の予想更新で消えることはありません。

### 予想だけを表示する画面

```
[keiba_race_selector view="prediction"]
```

レース結果と同じ「競馬場を選ぶ → レースを選ぶ」の操作で、予想だけを表示します。
LINEアプリ内で開かれる想定のため、14列の結果表ではなく馬番・馬名・印の3列に絞っています。

## ページキャッシュに注意（実際に障害になった）

サイトにはWP Rocketが入っており、**投稿を更新してもキャッシュが残っていると
朝に生成された「出走表だけ」のHTMLが配信され続けます**。

2026-08-05の実測:

| ページ | キャッシュ生成 | 投稿の更新 | 着順の表示 |
| --- | --- | --- | --- |
| 園田12R | 08:22 | 17:22 | されない |
| 船橋5R | 10:15 | 17:22 | されない |
| 門別6R | キャッシュ無し | 17:22 | される |

キャッシュが無いページだけ正しく表示されるため、**「一部のレースだけ更新される」**
という分かりにくい形で表面化します。収集アプリ側のログが「反映完了」でも、
サイトには出ていないことがある点に注意してください。

プラグイン v0.1.3 以降は、メタ更新時に該当レースページとレース一覧ページの
キャッシュを自動で破棄します（`keiba_race_sync_purge_post_cache`）。
WP Rocket / WP Super Cache / W3 Total Cache / WP Fastest Cache / LiteSpeed /
Cache Enabler に対応。他の仕組みを使う場合は `keiba_race_sync_purge_post`
アクションで追加できます。

確認方法（キャッシュを迂回すると出るなら、キャッシュが原因）:

```powershell
# 通常アクセス
(Invoke-WebRequest 'https://www.keiba-tips.top/race/<slug>/' -UseBasicParsing).Content -match 'keiba-result-table'
# クエリ付き＝キャッシュ迂回
(Invoke-WebRequest 'https://www.keiba-tips.top/race/<slug>/?nocache=1' -UseBasicParsing).Content -match 'keiba-result-table'
```

HTML末尾の `Debug: cached@<unixtime>` でキャッシュ生成時刻が分かります。

## データ源ごとの項目の入り方（実測）

地方競馬（UmaConn）は、成績レコード(SE)に入れてくる項目が**競馬場によって異なります**。
「地方競馬だから一律に取れない」ではない点に注意してください。

2026-08-03 の本番データを実測した結果（各レース1R、「入っている頭数／全頭数」）:

| 競馬場コード | 後3F | 単勝オッズ | 斤量 | 馬体重 |
| --- | --- | --- | --- | --- |
| 35 盛岡 | 12/12 | 12/12 | 12/12 | 12/12 |
| 43 船橋 | 9/9 | **0/9** | 9/9 | 9/9 |
| 46 金沢 | 8/8 | 8/8 | 8/8 | 8/8 |
| 83 ばんえい | **0/9** | 9/9 | 6/9 | 2/9 |

読み取れること:

- **後3ハロンタイム**は通常の地方競馬場では取得できる。
  ばんえい(83)のみ入らないが、200m直線競走でハロンの概念が無いため妥当。
- **単勝オッズ・人気順**はSEに入らない競馬場がある（船橋43など）。
  そのため速報オッズ `0B31` のO1レコードから補完している（`RaceResultService`）。
  SE側に実値がある場合は上書きしないため、中央競馬や盛岡・金沢の挙動は変わらない。
- **ばんえい(83)は負担重量・馬体重が不完全**。通常の地方競馬場では正常。詳細は下記。

バイト位置のズレではないことは確認済み（同レコード内の着差コード=343バイト目が
正しく読めるため、その後ろの単勝オッズ=360・人気順=364・後3ハロン=391もズレていない）。
値が入らないケースは、データ源がその項目を送っていないことによる。

### 未提供の項目は数値ではなく「－」で表示する

`0` は上記いずれの項目でも有効な値になり得ないため、そのまま出すと
「1番人気」「オッズ0倍」「馬体重0kg」に見えてしまいます。
プラグイン側で未提供と分かる表示に変換しています
（`keiba_race_sync_num_text` / `keiba_race_sync_bataiju_text`）。

### ばんえい(83)の負担重量は表示していない

ばんえいの負担重量は馬が曳く「そり」の重量で、規定は**最低480kg（牝馬460kg）〜最高1000kg**。
ところが実データから得られる値は 24.4〜28.0 で、どう読んでも規定の範囲に入りません
（2026-08-10の実測: 全118頭中、値が入るのは46頭のみ、残り72頭は0）。

生値(244/258/262/276/280)を2.5倍すると610/645/655/690/700kgと妥当な範囲の5の倍数になりますが、
係数2.5に根拠がなく、牝馬の減量幅(20kg)とも合いません。**数頭分の一致で換算式を決めないこと。**

そのためプラグイン側で、ばんえいの斤量は「－」と表示しています
（`keiba_race_sync_kinryo_text`）。保存データは加工していないので、
正しい換算が判明したらこの関数だけを直せば復活できます。
検証には公式出走表の負担重量との突き合わせが必要です。

平地（中央・盛岡・浦和・金沢等）は50〜58kgで正常なため、影響はばんえいのみです。

## 機密情報の扱い

`App.config` には非機密の既定値のみをコミットしています。利用キー・パスワード類は
**環境変数**（`AppConfig.cs` が環境変数を優先して読む）で実行時に注入してください。
`App.config` に実際の値を書き込んでコミットしないよう注意してください。
